Allowlist central gate `src/workspaces.ts:513 resolveWorkspaceTarget`.

## Goal

Ship a host-adoptable batched read that delivers most round-trip savings (N reads → 1 RTT) while preserving per-file allowlist + per-file auditability, validated with real ChatGPT/Claude clients before expanding. Measure performance impact of byte limits before finalizing.

Out of scope (explicitly deferred): `execute_script`/`node_eval`, `node_repl` bridging (designed separately below).

## Proposed Shape — `multi_read` (chosen)

### Naming
- Canonical: `multi_read` in `CANONICAL_TOOL_NAMES` (hash recompute at `src/tool-contract.ts:65-86`).
- No alias; description nudges: "prefer `multi_read` over N× `read_file`".
- Gate: `experimental.multi_read` until validated, then promote (or ship unconditionally; flag minimal risk).

### Input schema (Zod → JSON Schema)
```ts
multi_read: z.object({
  workspaceId: z.string().min(1).max(128),
  reads: z.array(z.object({
    path: z.string(),
    offset: z.number().int().positive().optional(), // mirror read_file
    limit: z.number().int().positive().optional(),
  })).min(1).max(20),
  maxBytesPerFile: z.number().int().positive().max(2_000_000).optional(), // provisional — measure, see Verification:2
  maxTotalBytes: z.number().int().positive().max(10_000_000).optional(),
})
```
Limits enforced *before* I/O; reject 400 if exceeded. No `stopOnError` — always continue, per-file errors. See Verification (2) for performance testing of limits before finalizing defaults.

### Output schema
```ts
{
  results: Array<{
    path: string,
    canonicalPath?: string,
    status: "ok" | "error",
    content?: string,
    truncated?: boolean,
    bytes?: number,
    error?: { code: string, message: string }
  }>
}
// Host-visible _meta: { cards: ToolResultCard[] } one card per file
// Transport: single MCP tools/call, aggregated structuredContent
```
Top-level error only for invalid workspaceId or limit breach; partial success is success.

### Execution location
- Register in `src/server.ts: createMcpServer` via `registerAppTool("multi_read", {inputSchema, outputSchema, annotations: {readOnlyHint:true}})` — same pattern as `read_file:1229-1293`.
- Handler loops `reads[]`, for each entry:
  1. `resolveWorkspaceTarget(workspace, path, "read")` at `src/workspaces.ts:513` — lexical + canonical + policy check (reuse `isPathInsideRoot`).
  2. Delegates to existing read path (`pi-tools.readFileTool` / `fs.read` via `executor.read` internals) — reuse `executor.ts:280-285` logic.
  3. Calls `logToolExecution("read_file", ...)` per file (at `src/executor.ts:115-135`) and appends gateway activity per file via `GatewayExecutionRouter` fan-out (one `operationId` per sub-op at `src/gateway-router.ts:236-253`), so N log entries + N cards + N activity events, not one aggregated.
  4. Aggregates into `results[]` + `_meta.cards[]`.

- Gateway path: `GatewayExecutionRouter.execute` must handle `multi_read` by looking up binding once, then fanning sub-reads to same `target` (via `targetFor(machine)`), preserving `requestId` parent + per-sub-op suffix for tracing. No new target logic needed.
- Local path: `LocalExecutor.execute` dispatch adds `case "multi_read"` that calls new `readMany` helper looping `resolveReadPath`.

### Resumability
- Reads are idempotent → outer `multi_read` with fingerprint `sha256(JSON({tool,args}))` at `src/node-server.ts:243-245` is safe to mark resumable (replay from `operations` cache if remote). No per-sub-op dedup needed. Writes deferred avoids ambiguous outer dedup.

## node_repl Bridge — per-session isolated (per your proposal, independent of sky-cua)

### Requirements you stated (updated)
- Gated with `DISABLED_CAPABILITIES=node_repl` (per-session header `X-Disabled-Capabilities` + global `DISABLED_CAPABILITIES` env, same as `sky-cua` at `src/server.ts:1612-1613` `isSkyCuaDisabled(effectiveSet)`).
- Independent of `sky-cua` — own lifecycle, own disable flag, own health.
- One process per MCP session, auto-cleanup when session doesn't reconnect — isolates users, prevents cross-user REPL contamination.
- Persistent enough for reconnect: survives *transient* disconnect within session TTL, but not across distinct sessions.

### Why per-session is correct (you're right)
Server-singleton would share `var` heap across users/sessions — a Sarah tab and a ChatGPT tab would see each other's `var scratch = ...`, which is contamination. Per-session gives isolation. Your "auto-cleanup of sessions that don't reconnect" already exists at `src/server.ts:1944-1977` `sweepTimer` (evicts idle `transports`/`lastActiveAt` after `config.sessions.idleTtlSeconds`), so tying REPL lifecycle to session lifecycle reuses that.

### Recommended: Per-session NodeReplBridge with deferred cleanup

- **Process:** Not one global `nodeReplBridgeCache`, but `sessionNodeReplBridges: Map<sessionId, NodeReplBridge>` (keyed by `StreamableHTTPServerTransport.sessionId`, mirrored with `sessionEffectiveDisabled` at `src/server.ts:1690-1691`). On `createMcpServer` for a new `initialize`, if `!isNodeReplDisabled(effective)` for that session's `pendingEffectiveDisabled` (already computed at `src/server.ts:1857-1896`), lazily spawn `node_repl` child via `StdioClientTransport` to `bin/node_repl` (`opencode.jsonc:308-317` `command: ~/.local/share/sky-cua/bin/node_repl`) on first `js` call (or eagerly on initialize if you want `listTools` early). Store bridge in map keyed by `sessionId` assigned in `onsessioninitialized` at `src/server.ts:1869-1873`.
- **Tool exposure:** Same as sky-cua pattern but per-session: if session's `effective` doesn't contain `node_repl`, enumerate `bridge.tools` (`js`, `js_add_node_module_dir`, `js_reset`) via `listTools` → `jsonSchemaToZod` (`src/sky-cua/bridge.ts:155-209` pattern) → `registerAppTool` at `src/server.ts:1609-1665` for that `McpServer` instance only. If session later sends `X-Disabled-Capabilities: node_repl`, don't register (per-session gate). Independence via own `DISABLED_CAPABILITIES` key `node_repl`, own optional `DEVSPACE_NODE_REPL_BIN` env, not sharing `skyBridgeCache`.
- **Persistence across transient glitch:** Do **not** kill on `transport.onclose` immediately (glitch would lose `var` heap). Instead, keep bridge in `sessionNodeReplBridges` after `transport.close` fires at `src/server.ts:1884-1894`, and only evict on `sweepTimer` idle eviction (same TTL as MCP session, `config.sessions.idleTtlSeconds` default 1800s at `src/config.ts:397-398`). Reconnect within TTL: new `StreamableHTTPServerTransport` reuses same `sessionId`? Currently DevSpace creates new `sessionId` per `initialize` (`sessionIdGenerator: () => randomUUID()` at `src/server.ts:1868`), so strictly a reconnect is a *new* session and would get a new REPL — that's isolation by design. If you want true resume within TTL (same `sessionId` resumed), need to add session-resume mapping (store bridge keyed by any sessionId that was issued, not just active transport). For now, accept that glitch = new session = new REPL (clean), but not server-wide contamination. If later you want sticky resume, key bridges by a stable client token, not transport.
- **Lifecycle edge:** On `transport.close`, keep entry in `sessionNodeReplBridges` + `lastActiveAt` entry; on `sweepTimer` eviction loop where `now - lastActive >= ttl`, close the bridge (`bridge.close()`) and delete map entry alongside `transports.delete(sessionId)` at `src/server.ts:1953-1956`. Also close on `RunningServer.close()` at `src/server.ts:1982-1996`.
- **Concurrency & isolation:** Per-session serializes per bridge (one `StdioClientTransport` per session), so two `js` calls from same session queue naturally; cross-session calls don't interfere (separate processes). Document that within a session `var` bindings persist across `js` calls until `js_reset` or session eviction — agents should still use IIFE array-join pattern (`await (async()=>{...})()` via `tools.node_repl.js`) for one-shot work to avoid leaking, unless intentional `var` persistence needed for that session's transformations.
- **Resource bound:** Per-session means `N` concurrent sessions = `N` node processes. Bound via same `config.sessions` limits + optional `maxNodeReplPerHost` (e.g., 12, mirroring terminal limits at `src/config.ts:381-384`). Reject new `js` with 503 if over cap, same as node capacity handling at `src/node-server.ts:149-152`.
- **Allowlist / audit:** `node_repl` is **not** workspace-root-gated (full JS VM). Gate via `DISABLED_CAPABILITIES` + `logToolExecution("node_repl_js")` per call for audit, same as other tools. Host filesystem access via `node:fs/promises` is still host-dependent — document that agents must pass explicit `workspaceRoot` if they read host files.

### Keep separate from `multi_read`
`multi_read` stays declarative data-access (auditable per-file via `src/workspaces.ts:513`), `node_repl` stays imperative per-session compute. Don't unify — avoids `multi_read` becoming `execute_script` lite.

### Trade-off summary for per-session node_repl (your proposal)
- Pro: Isolation (no cross-user var contamination), natural lifecycle tied to existing session sweep, independent gate, enables per-session co-located transformations without N RTTs, reuses OpenCode-trusted binary.
- Con: Glitch within TTL still gets new REPL (clean but loses transient vars) — acceptable for isolation; if you later want sticky resume, need stable session resume key. Per-session process count scales with sessions (needs cap).

## Risks
- Hash break if later switching canonical (multi_read→batch or vice versa) — now mitigated by choosing read-only `batch` that subsumes `multi_read`; 2nd break unlikely.
- Host non-adoption of polymorphic `batch` — mitigated by restricting to 4 read-only tools + rich description + examples; fallback to typed `multi_read` alias over same backend is cheap.
- Path traversal inside batch — mitigated by per-entry `resolveWorkspaceTarget` (or per-op target resolution for grep scope), not outer check only.
- Large batch DoS — enforced limits before I/O.
- `node_repl` shared state surprise — mitigated by docs: use IIFE/array-join pattern for one-shot work, `var` only for intentional persistence; serialize calls.
